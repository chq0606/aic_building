================================================================
建筑能耗分析与节能优化平台 - 分步实施提示词（v1）
================================================================

【全局背景】
本项目参加 2026 全球校园人工智能算法精英大赛 AI 场景建造赛道。
定位：面向多租户建筑群的 AI 能效诊断与节能优化平台。
不绑定特定数据集，不写死分析逻辑，搭一个能换数据、能接客户、
能追溯证据的产品底座。

【部署模型】
开源自部署项目，每个使用者 clone 代码后跑在自己本地，每个本地
实例是独立的数据库，互不干扰。不存在"多用户共用一个服务器"
的 SaaS 场景。基于这个前提：
- 不需要担心某个用户的操作影响其他人（实例隔离）
- "一人一租户"指的是同一本地实例内，不同注册用户数据隔离
- demo 体验账号是出厂自带的只读账号，clone 后默认可用
- reset / seed 这类运维操作对所有登录用户开放，不存在滥用问题

【已落地工作】
- 数据库层：PostgreSQL 15 + pgvector 0.8.3
- 建表 SQL：postgresql_bdg2.sql（5 schema / 17 表 / 3 视图 / 20 索引）
- demo seed 脚本：code/seed_bdg2.py（已跑通）
- demo 数据：1 tenant(demo) / 1 site(Bobcat) / 6 buildings / 28 points
            169,146 point_readings / 8,744 weather_readings / ~12,000 日聚合
- 知识库表为空，等文档导入

Step 02：注册 + 登录（一人一租户）
================================================================

【背景】
参考 RAGFlow 的注册模式：访客打开网站 → 注册账号 → 登录。
但本项目是开源自部署，每个使用者跑一个实例。
做法：一人一租户——每个用户注册时自动创建一个独立租户，
用户绑定为该租户的 admin，不同用户数据天然隔离。

不做 RBAC（一人一租户不需要角色分级）。
不做 super admin（没有跨租户管理场景）。
不做租户管理界面（用户只看自己的租户信息）。
不做邀请码/加入已有租户（不支持同租户多人协作）。

demo 租户已有 BDG2 数据（6 栋楼 / 16.9 万行读数），作为"体验账号"
独立提供，登录页有"体验 demo"按钮，用 demo / demo123 登录后只读访问。

【目标】
实现注册 + 登录 + JWT + 多租户隔离。每个注册用户 = 一个新租户。

【输入】
- Step 01 的后端骨架
- core.tenant 表（已存在，里面已有 demo 一行）
- core."user" 表（已通过 auth_bdg2.sql 建好，空表）

【输出】
- backend/app/models/auth.py
  - RegisterRequest / LoginRequest / TokenResponse / UserOut / ChangePasswordRequest
- backend/app/core/security.py
  - 密码哈希：bcrypt
  - JWT 生成与校验：python-jose
- backend/app/core/deps.py
  - get_current_user（依赖注入，从 JWT 解析用户）
  - get_current_tenant_id（返回当前用户的 tenant_id）
- backend/app/api/auth.py
  - POST /api/v1/auth/register（注册：用户名+密码+邮箱(可选) → 创建租户+用户 → JWT）
  - POST /api/v1/auth/login（用户名+密码 → JWT）
  - POST /api/v1/auth/refresh
  - GET /api/v1/auth/me（当前用户信息 + 租户信息）
  - POST /api/v1/auth/change-password（修改自己密码）
- backend/app/seed/demo_user.py
  - 后端启动时调用：检测 demo 租户是否已有 demo 用户，没有则创建
    demo / demo123，标记为只读（is_active=true 但无法改数据，通过业务 API 逻辑判断）

【技术要求】
1. 注册流程：
   - 请求：{username, password, email(可选)}
   - 后端校验：username 不重复（跨所有租户全局唯一）
   - 后端创建：core.tenant 一行（tenant_code = "user_" + username，
     tenant_name = username），core."user" 一行（绑定到新 tenant）
   - 返回 JWT
2. 登录流程：
   - 请求：{username, password}
   - 后端查 core."user" 表，bcrypt 比对密码
   - 正确 → 返回 JWT（payload 含 user_id, tenant_id, username）
   - 错误 → 返回 401
3. JWT 过期时间 24h，refresh 7d
4. 所有业务 API 用 get_current_user 依赖注入校验登录态
5. 所有业务查询强制带 tenant_id = current_user.tenant_id
6. demo 用户（username = 'demo'）的特殊处理：
   - 业务 API 检测到当前用户是 demo 用户时，写操作（上传/改/删）返回 403
   - 读操作正常放行
7. username 全局唯一（不是 tenant 内唯一），用 username 直接登录
8. 密码强度校验：最少 8 位，包含字母和数字
9. change-password 接口要求带旧密码
10. 不做用户列表 API（用户只看自己）
11. 不做角色、权限、user_role、role_permission 四张表

【依赖】
- Step 01 后端骨架
- auth_bdg2.sql 已执行（core."user" 表已建）

【验收标准】
- 注册新用户 → 能登录 → 看到空租户（无楼无数据）
- 用 demo / demo123 登录 → 看到 6 栋楼 + 16.9 万行读数
- demo 用户尝试上传数据 → 返回 403
- 普通用户尝试查其他租户数据 → 查不到（强制 tenant_id 过滤）
- 重复 username 注册 → 返回 409
- 能修改自己密码

Step 04：客户数据上传与字段映射
================================================================

【背景】
赛题要求"数据集构建与导入接口"。项目面向真实客户，客户数据格式
千差万别。原 Step 8 全集太重，本步做成三层级方案，客户自选。

【目标】
实现三层级客户数据上传：极简（单 CSV 自动识别）/ 标准（CSV + 字段映射）
/ 完整（多文件 + 映射向导）。内部统一 canonical long format。

【输入】
- ingest.upload_file / ingest.mapping_profile 表（已存在）
- Step 02 简单认证（需登录）

【输出】
- backend/app/models/upload.py（Pydantic schema）
- backend/app/models/mapping.py
- backend/app/services/upload_service.py
- backend/app/services/mapping_service.py
- backend/app/services/wide_to_long.py（宽表转长表，支持 .xlsx 和 .csv）
- backend/app/api/upload.py
  - POST /api/v1/uploads/single（层级 A：单 CSV 自动识别）
  - POST /api/v1/uploads/multi（层级 C：多文件上传）
  - GET /api/v1/uploads/{id}/mapping-suggest（自动猜测列映射）
  - POST /api/v1/uploads/{id}/mapping（层级 B/C：确认或调整映射）
  - POST /api/v1/uploads/{id}/validate（校验）
  - POST /api/v1/uploads/{id}/commit（确认导入，进 staging）
  - GET /api/v1/uploads（列表，按 tenant 过滤）

【技术要求】
1. 层级 A：上传单 CSV，后端读 header，用 mapping_profile 的默认规则
   自动匹配列名（building_id/energy_type/timestamp/value 等），
   直接进 staging，返回导入结果。失败时返回详细错误。
2. 层级 B：上传 CSV → 调 /mapping-suggest 返回列名猜测 →
   用户调整 → /mapping 保存 → /validate 校验 → /commit 导入。
3. 层级 C：上传 buildings.csv + readings.csv + weather.csv 三个文件，
   每个文件独立走映射向导，最后统一 commit。
4. 宽表转长表：支持 Excel 多 sheet、支持 melt 操作，输出统一 long format
5. mapping_profile 表存"列名映射 / 时间格式 / 单位映射 / 时区映射"，
   支持租户级别复用
6. 校验规则：必填字段非空、timestamp 格式合法、value 数值合法、
   building_id 在 core.building 存在（或自动创建）
7. 任何校验错误不能写入 fact 表，只能停在 staging
8. 内部 canonical format 固定 long，宽表必须先转 long

【依赖】
- Step 01 后端骨架
- Step 02 RBAC
- Step 03 seed（参考 staging 灌入逻辑）

【验收标准】
- 层级 A：拖一个符合格式的 CSV，自动导入成功
- 层级 B：上传 CSV 后能看到列名猜测，调整后导入成功
- 层级 C：三文件上传，分别映射后统一导入成功
- 宽表 Excel 能正确转 long 后导入
- 错误数据（缺 timestamp / value 非数字 / building_id 不存在）被拦截

【输入】

【输出】

Step 08：异常检测服务
================================================================

【背景】
异常检测是节能优化的核心信号。原计划 5 类异常扩到 6 类，加
BASELINE_DEVIATION（横向对比异常，同类型建筑单位面积能耗偏高）。
删掉 zone-level，只做 building-level。

【目标】
实现 6 类异常检测，结果写入 mart.anomaly_event，提供建筑级异常
查询 API。先做可解释规则版，LLM 不进主链路。

【输入】
- fact.point_reading
- mart.building_daily_energy
- core.building（primary_use / sqm 用于横向对比）

【输出】
- backend/app/services/anomaly_service.py
- backend/app/services/anomaly_detectors/（每类一个文件）
  - spike.py（瞬时尖峰）
  - drift.py（缓慢漂移）
  - prolonged_zero.py（持续为零）
  - missing_gap.py（缺测时段）
  - schedule_violation.py（作息违反，周末/夜间异常高负荷）
  - baseline_deviation.py（横向对比异常，EUI 高于同类均值）
- backend/app/api/anomaly.py
  - POST /api/v1/anomalies/detect?building_id=&time_range=（触发检测）
  - GET /api/v1/anomalies/buildings/{building_id}
  - GET /api/v1/anomalies/sites/{site_id}/overview
  - GET /api/v1/anomalies/{id}/evidence（异常的证据链）

【技术要求】
1. 6 类异常：
   - SPIKE：单点值超过近 7 天均值 + 3σ
   - DRIFT：7 天滑动均值偏离历史均值超过 20%
   - PROLONGED_ZERO：连续 ≥ 6 小时值为 0（且该 point 不该为零）
   - MISSING_GAP：应有读数但缺失超过 3 小时
   - SCHEDULE_VIOLATION：非工作时段（夜间 22:00-6:00 或周末）
                         负荷超过工作时段中位数的 50%
   - BASELINE_DEVIATION：EUI 高于同 primary_use 建筑均值 + 1σ
2. 每个异常记录：observed_value / baseline_value / evidence（JSON）
3. evidence 字段存可追溯证据：时段、对比基准、相关数据点
4. 检测可手动触发（API），也可配置定时任务（用 APScheduler，非必须）
5. LLM 不进异常检测主链路，但 evidence 字段为 AI 助手提供素材
6. building-level 检测，每个 building 跑一次覆盖所有 point

【依赖】
- Step 07 查询 API（复用部分查询能力）

【验收标准】
- 对 Bobcat 6 栋楼触发检测，能输出异常列表

【输出】
- prediction_bdg2.sql（独立 SQL 文件，建 mart.prediction_job 表）
- backend/app/services/prediction_service.py
  - predict_prophet(building_id, horizon)：Prophet 跑历史 90 天
  - predict_lstm(building_id, horizon)：PyTorch LSTM 跑单楼 demo
  - evaluate_mape(actual, predicted)：算 MAPE 评估精度
- backend/app/worker/prediction_worker.py（异步消费 prediction_job 队列）
- backend/app/api/prediction.py
  - POST /api/v1/prediction/buildings/{id}/forecast?horizon=30d&model=prophet
  - GET /api/v1/prediction/jobs/{id}
  - GET /api/v1/prediction/buildings/{id}/latest（取最近一次预测结果）
- 修改 Step 15 分析中心页，新增 PredictionPanel.vue
  - 折线图：实线历史 + 虚线预测 + 置信区间阴影
  - 模型切换：Prophet / LSTM 对比
  - MAPE 显示

【技术要求】
1. prediction_job 表字段：id / tenant_id / building_id / model_type
   (prophet/lstm/linear) / horizon_days / status / mape / result_jsonb /
   started_at / finished_at / error_message / created_at
2. 状态机：PENDING → RUNNING → SUCCEEDED / FAILED
3. Prophet 实现：
   - 取该楼历史 90 天日粒度数据（来自 mart.building_daily_energy）
   - 用 prophet 库训练，yearly_seasonality / weekly_seasonality 自动
   - 输出 horizon 天预测 + yhat_lower / yhat_upper 置信区间
   - 用最后 7 天实际值算 MAPE
4. LSTM 实现（demo 级别）：
   - 取该楼历史 90 天日粒度数据
   - 滑动窗口构造样本：window=14 天 → predict 第 15 天
   - 模型：LSTM(input=1, hidden=32, num_layers=2, output=1)
   - 训练 50 epoch，CPU 跑（不依赖 GPU）
   - 输出 horizon 天预测，无置信区间（或用 dropout MC 估计）
   - 用最后 7 天实际值算 MAPE
5. result_jsonb 结构：
   {history: [{date, value}], forecast: [{date, yhat, yhat_lower, yhat_upper}],
    mape: 12.5, model_type: "prophet"}
6. 异步任务：用 PostgreSQL 表 + SELECT FOR UPDATE SKIP LOCKED 轮询
   （与 Step 12 TripoSplat worker 同一套机制）
7. worker 独立进程：python -m worker.prediction_worker
8. 预测 API 需登录（get_current_user 依赖）
9. 预测结果强制 tenant_id 隔离

【依赖】

- Step 07 查询 API（取历史时序）
- Step 15 分析中心页（嵌入 PredictionPanel）

【验收标准】

- MAPE < 20% 算可用
- LSTM demo 能跑通至少 1 栋楼
- 前端 PredictionPanel 渲染实线历史 + 虚线预测 + 置信区间阴影
- 模型切换 Prophet / LSTM 能对比 MAPE
